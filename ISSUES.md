# Реестр дефектов — Finance Tracker API

Данный документ содержит дефекты кодовой базы и недоработки, обнаруженные при составлении спецификации требований и верификации приложения.

---

## ISSUE-001: Неиспользуемая таблица для модуля бюджетов

| Поле | Значение |
|------|----------|
| **Приоритет** | Средний |
| **Тип** | Технический долг |
| **Статус** | Открыт |
| **Компонент** | База данных / Доменная модель |
| **Дата обнаружения** | 2026-10-06 |

**Описание:**
В базе данных существует таблица `budget`. Она инициализируется в миграции `V1__init_schema.sql` (поля `id`, `user_id`, `category_id`, `month_year`, `limit_amount`). Однако в Java-коде полностью отсутствует модуль для работы с бюджетами: нет контроллера, сервиса, репозитория и доменной сущности.

**Ожидаемое поведение:**
Схема базы данных должна соответствовать реализованному функционалу (YAGNI). Если функционал бюджетов не реализован, таблицы не должно быть в БД.

**Фактическое поведение:**
Таблица `budget` создаётся при запуске, но никак не используется приложением.

**Шаги воспроизведения:**
1. Проверить файл `src/main/resources/db/migration/V1__init_schema.sql`.
2. Выполнить поиск по проекту компонентов, связанных с `budget`.

**Рекомендация по исправлению:**
Либо реализовать REST API для управления бюджетами (создать `BudgetController`, `BudgetService` и т.д.), либо удалить таблицу `budget` из схемы базы данных в новой миграции.

## ISSUE-002: Отсутствие операций обновления и удаления (CRUD)

| Поле | Значение |
|------|----------|
| **Приоритет** | Средний |
| **Тип** | Неполная реализация |
| **Статус** | Открыт |
| **Компонент** | Модули Account, Transaction, Category |
| **Дата обнаружения** | 2026-10-06 |

**Описание:**
Для всех основных сущностей системы (Account, Transaction, TransactionCategory) реализованы только операции создания (POST) и чтения (GET). Отсутствуют методы для изменения и удаления ошибочно введенных данных. Схема БД при этом готова к удалению (настроено каскадное удаление `ON DELETE CASCADE` для внешних ключей).

**Ожидаемое поведение:**
REST API для управления финансами должно предоставлять пользователю возможность редактировать и удалять свои записи.

**Затронутые эндпоинты (отсутствующие):**
- `PUT /api/accounts/{id}`
- `DELETE /api/accounts/{id}`
- `PUT /api/transactions/{id}`
- `DELETE /api/transactions/{id}`
- `DELETE /api/categories/{id}`

**Рекомендация по исправлению:**
Добавить эндпоинты обновления и удаления с обязательной валидацией прав владения ресурсом (`userId` из токена = `userId` владельца ресурса).

## ISSUE-003: Не верифицировано требование к производительности NFR-02

| Поле | Значение |
|------|----------|
| **Приоритет** | Низкий |
| **Тип** | Отсутствие тестирования |
| **Статус** | Открыт |
| **Компонент** | Тестирование производительности |
| **Дата обнаружения** | 2026-10-06 |

**Описание:**
Нефункциональное требование NFR-02 гласит: "Время ответа API для типовых CRUD-операций не должно превышать 500 мс при нагрузке до 100 одновременных пользователей". Данное требование не может быть верифицировано вручную.

**Ожидаемое поведение:**
В проекте настроено автоматизированное нагрузочное тестирование.

**Фактическое поведение:**
Сценарии нагрузочного тестирования отсутствуют.

**Рекомендация по исправлению:**
Создать тестовые скрипты для JMeter или Gatling и провести нагрузочное тестирование для подтверждения соответствия NFR-02.

## ISSUE-004: Возможность ухода баланса в неконтролируемый овердрафт (DEF-001)

| Поле | Значение |
|------|----------|
| **Приоритет** | Высокий |
| **Тип** | Бизнес-логика / Дефект валидации |
| **Статус** | Открыт |
| **Компонент** | Модуль Transaction (`TransactionServiceImpl`) |
| **Дата обнаружения** | 2026-10-27 |

**Описание:**
При создании транзакции типа EXPENSE на сумму, превышающую текущий остаток на счёте, система списывает средства без проверки достаточности баланса, в результате чего баланс счёта становится отрицательным.

**Ожидаемое поведение:**
Для счетов типов CARD (дебетовая) и CASH при попытке списания средств сверх остатка операция должна блокироваться с ошибкой `HTTP 400 Bad Request: "Insufficient funds on account"`.

**Фактическое поведение:**
Транзакция проводится (`HTTP 201 Created`), а баланс счёта уходит в отрицательное значение.

**Шаги воспроизведения:**
1. Создать счёт с начальным балансом 0.00.
2. Провести транзакцию EXPENSE на сумму 500.00.
3. Проверить баланс счёта — он равен -500.00.

**Рекомендация по исправлению:**
Добавить в `TransactionServiceImpl` проверку остатка перед вызовом `adjustBalance()` и выбрасывать доменное исключение `InsufficientFundsException` при попытке овердрафта.

## ISSUE-005: Ошибка HTTP 500 вместо валидации HTTP 400 при превышении длины строк (DEF-002)

| Поле | Значение |
|------|----------|
| **Приоритет** | Средний |
| **Тип** | Валидация входных данных |
| **Статус** | Открыт |
| **Компонент** | API DTO (`CreateAccountRequest`, `CreateCategoryRequest`) |
| **Дата обнаружения** | 2026-10-27 |

**Описание:**
Поля имён сущностей (`name`) и описания транзакций (`description`) в DTO не содержат аннотации `@Size(max = 255)`. При передаче клиентом строки длиннее 255 символов ошибка валидации на уровне Spring не генерируется, запрос уходит в СУБД, где падает с `DataIntegrityViolationException`, возвращая клиенту неинформативную ошибку `HTTP 500 Internal Server Error`.

**Ожидаемое поведение:**
Клиенту должен возвращаться ответ `HTTP 400 Bad Request` в формате RFC 7807 с сообщением о превышении допустимого размера строки.

**Фактическое поведение:**
Возвращается `HTTP 500 Internal Server Error`.

**Шаги воспроизведения:**
1. Отправить POST запрос на `/api/accounts` со строкой `name` длиной 300 символов.
2. Сервер возвращает код 500.

**Рекомендация по исправлению:**
1. Разместить аннотации `@Size(max = 255)` на строковых полях входных DTO.
2. Добавить перехватчик `DataIntegrityViolationException` в `GlobalExceptionHandler` с возвратом статуса `HTTP 400 Bad Request` или `HTTP 409 Conflict`.
